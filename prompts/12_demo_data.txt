================================================================
제품 컨텍스트
================================================================
빈 화면에서 시작하면 관계 지도가 안 보이고, 실시간 분석 대기 시간이 길어져 시연이 끊긴다.
무료 티어 rate limit 때문에 데모 직전 연속 업로드 테스트는 위험하다.
사전 데이터는 미리 분석해 DB에 넣어두고, 실시간 Gemini 호출은 시연 1건으로 제한한다.

주제: "교내 카페 개선안" — 같은 문제를 세 전공이 다르게 푸는 모습을 보여준다.

================================================================
시드 구성
================================================================
스페이스
  name: 교내 카페 개선안
  joinCode: 고정값 허용 (예: CAFE01) — 발표자가 외울 수 있게

멤버 최소 3명 (학교/전공이 서로 다르게):
  1) 산업공학 / 동선·대기열
  2) 컴퓨터공학 / 앱·센서·예측
  3) 경영/디자인 등 / 공간·메뉴·경험
  닉네임은 발표 팀원 실명 또는 가명.

결과물 6~7건 가이드 (내용은 직접 작성하되 아래 클러스터가 나오게 쓴다):
  클러스터 A 대기시간 (최소 3건, 전공을 섞는다)
    - 대기열 재배치, 피크타임 예측, 모바일 주문 번호표 등
    - 유사도가 0.75를 넘도록 같은 문제의식(대기)을 공유하고 해법은 다르게
  클러스터 B 공간/좌석 (2건)
  단독 1건 (고의로 다른 주제, 예: 알레르기 메뉴 표시)
  시연용으로 비워 둘 슬롯 1개: "실시간 업로드 시연" — 시드에 넣지 않는다.

시드 방식 (택1, 둘 다 되면 더 좋음):
  A) CommandLineRunner / data.sql 로 Space, Member, Artifact, Group 을 직접 insert
     tags, embedding, group, 정리본까지 채운다. 데모 시작 시 Gemini를 부르지 않는다.
  B) JSON 파일을 읽어 시딩하는 스크립트 또는 admin POST
     README에 "데모 시드 실행 방법"을 적는다.

중요: A를 권장한다. 임베딩을 당일 재계산하면 rate limit과 지연이 시연을 죽인다.
임베딩 값은 07단계를 로컬에서 한 번 돌려 얻은 벡터를 파일로 저장해 넣거나,
그룹 배정을 시드에서 직접 넣고 embedding은 더미 벡터로 두어도 된다.
단, 시연 중 새로 올리는 1건은 실제 임베딩이 필요하므로 파이프라인은 살아 있어야 한다.

시연용 실시간 1건 초안을 README 또는 /prompts 가 아닌 /demo/live-upload.md 에 적어 둔다.
발표자 B가 그대로 붙여넣을 수 있게 제목+본문을 완성한다.
이 1건은 클러스터 A(대기시간)에 합류하도록 대기/줄서기 문제를 다루되,
기존 3건과 다른 전공 관점이어야 한다. 그래야 정리본이 눈에 띄게 갱신된다.
