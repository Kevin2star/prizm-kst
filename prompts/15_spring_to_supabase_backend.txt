역할: 시니어 풀스택 엔지니어. Spring Boot 백엔드를 제거하고 서버를 Supabase로 대체한다.
선행 단계: 01~13 기능이 프론트에 있고, 14에서 DB를 Supabase Postgres로 맞춘 상태여도 된다.
  Spring이 아직 MySQL이어도 상관 없다. 이 단계에서 스키마는 Postgres에 다시 둔다.
이번 단계 목표: JDK/Spring/JPA/STOMP를 없애고, 같은 P0(F1~F6)를 Supabase만으로 동작시킨다.
다음 단계: 없음. 스택 교체 패치다. 새 제품 기능을 만들지 않는다.

================================================================
왜 이렇게 바꾸나
================================================================
14단계는 Spring이 JDBC로 Supabase에 붙는 것까지만 했다. 백엔드는 여전히 Java다.
이제는 API, 비동기 AI 파이프라인, 실시간 이벤트까지 Supabase에서 돌린다.
프론트는 localhost:8080 Spring을 더 이상 필요로 하지 않는다.

================================================================
고정할 아키텍처 (변경 금지)
================================================================
- 프론트: 기존 React (Vite). 화면·라우트·마인드맵·폴링 폴백 UX는 유지.
- DB: Supabase Postgres. 테이블 의미는 02_data_model.txt 와 같다.
  spaces, members, artifacts, artifact_groups
- 서버 로직: Supabase Edge Functions (Deno). Gemini 키는 여기에만 둔다.
- 실시간: Supabase Realtime (postgres_changes). STOMP/SockJS를 쓰지 않는다.
- AI: Gemini 단일 벤더. 프론트에서 Gemini를 호출하지 않는다.
  - 태깅·정리본: gemini-2.5-flash
  - 임베딩: gemini-embedding-001 (768차원)
- 벡터: embedding은 TEXT/JSON 문자열 컬럼. pgvector 도입 금지.
  코사인 유사도는 Edge Function 안에서 직접 계산한다.
- 인증: 로그인 없음. 6자리 joinCode. Supabase Auth(이메일/OAuth)를 켜서
  제품 로그인을 만들지 않는다. 멤버는 nickname+school+major 행이다.

금지:
- Spring Boot를 "게이트웨이"로 남기지 않는다. 전환이 끝나면 /backend Java는
  실행 경로에서 제거한다 (폴더 삭제 또는 README에서 obsolete 표시 후 더 이상 실행하지 않음).
- VITE_ 로 GEMINI_API_KEY 를 노출하지 않는다.
- Storage, Auth UI, Edge Functions 밖의 별도 Node/Express 서버를 새로 두지 않는다.

================================================================
보안 모델 (해커톤용, 이것만)
================================================================
테이블 RLS:
  - anon SELECT 는 허용해도 된다 (데모 규모, 공개 시연).
  - INSERT/UPDATE/DELETE 는 anon에게 주지 않는다.
  - 모든 쓰기는 Edge Function이 service role로 수행한다.
  - service role 키는 프론트에 넣지 않는다.

프론트가 가지는 것:
  VITE_SUPABASE_URL
  VITE_SUPABASE_ANON_KEY

Functions secrets:
  GEMINI_API_KEY
  GEMINI_TAG_MODEL, GEMINI_EMBED_MODEL (기본값 기존과 동일)
  SIMILARITY_THRESHOLD (기본 0.75)

================================================================
프론트 API 계약 (응답 JSON 모양을 깨지 말 것)
================================================================
기존 frontend/src/api.js 가 기대하는 동작을 그대로 맞춘다.
구현은 supabase.functions.invoke 또는 Functions HTTP URL로 바꿔도 된다.
메서드 이름과 화면이 쓰는 필드는 유지한다.

생성/입장
  POST createSpace({ name })
    → { id, name, joinCode }
  POST joinSpace(code, { nickname, school, major })
    → { id(memberId), spaceId, nickname, school, major }
    코드는 trim + 대문자. 없으면 SPACE_NOT_FOUND
  GET getSpace(id)
    → { id, name, joinCode, memberCount }

결과물
  POST createArtifact(spaceId, { memberId, title, content })
    → 즉시 반환. status=PENDING
    필드: id, spaceId, memberId, nickname, school, major, title, content,
          status, tags, groupId, createdAt
    HTTP는 201에 가깝게. 업로드 응답을 분석 완료까지 기다리지 않는다.
  GET listArtifacts(spaceId)
  GET getArtifact(id)   (원문 패널. embedding은 주지 않는다)

그룹/트리
  GET getGroup(id)
  GET getGraph(id)
    응답 스키마는 prompts/09_graph_api.txt 와 현재 GraphService 와 같게.
    프론트가 테이블을 조합해 트리를 만들지 않는다. graph는 서버(Function)가 조립한다.

헬스
  GET health → { "status": "ok" }
  Spring /api/health 를 대체한다.

에러 JSON (프론트가 message/error를 씀):
  { "error": "SPACE_NOT_FOUND", "message": "..." }
  한글 메시지는 기존 SpaceService/ArtifactService 톤을 따른다.

실시간 이벤트 (의미 유지, 전송만 교체)
================================================================
기존 타입을 유지하면 프론트 SpacePage 분기가 산다.
  ARTIFACT_ADDED   업로드 직후 (분석 전)
  GROUPS_UPDATED   그룹핑/정리본 끝난 뒤
  MEMBER_JOINED    입장 성공 뒤 (있으면 좋고, 없어도 P0)

구현 방법 (택1, 권장은 A):
  A) Function이 행을 쓴 뒤, 프론트는
     artifacts / artifact_groups postgres_changes 를 space_id 필터로 구독.
     INSERT artifacts → onEvent({ type: "ARTIFACT_ADDED", artifact })
     UPDATE artifact_groups 또는 artifacts.group_id 변경 → GROUPS_UPDATED
  B) Realtime Broadcast 채널 space:{id} 로 Function이 위 JSON을 보낸다.

frontend/src/realtime.js
  - @stomp/stompjs, sockjs-client 제거
  - connectSpaceRealtime(spaceId, onEvent) 시그니처는 유지
  - 연결 실패·지연 시 기존처럼 3초 POLL 폴백 (graph 재조회)
  - 페이지 unmount 시 구독 해제

핵심 UX: 메인 화면이 열린 채 다른 기기에서 올리면, 요청 버튼 없이 트리가 바뀐다.

AI / 그룹핑 (07·08 로직 이식, 언어만 Deno TS)
================================================================
createArtifact 흐름:
  1) artifacts INSERT status=PENDING, 즉시 응답 + ARTIFACT_ADDED
  2) 같은 요청을 막지 말고 백그라운드에서 분석
     (EdgeRuntime.waitUntil 또는 analyze-artifact Function 호출)
  3) PROCESSING → Gemini 태깅 → 임베딩 → tags/embedding 저장 → READY
  4) 기존 GroupingService.assignGroup 과 동일한 단순 알고리즘:
     같은 space의 READY 임베딩과 코사인 비교, 최댓값 >= threshold 이면 그 그룹
     (상대가 그룹 없으면 새 artifact_groups 생성 후 둘 다 배정)
     아니면 단독 잎으로 남김
  5) 그룹이 있으면 Gemini로 공통점/차이점/비고 갱신 (08 프롬프트 문안)
  6) GROUPS_UPDATED

실패: status=FAILED, 서버가 죽지 않음. 원문은 조회 가능.
키 없음: 실시간 업로드는 FAILED. 시드 데이터는 Gemini 없이 READY로 넣는다.
재시도: 태깅 JSON 파싱 실패 1회, 그래도 실패하면 tags=["미분류"].
         embedding 실패면 FAILED.
429: 짧게 로그 후 FAILED.
벡터DB/HDBSCAN/커뮤니티 디텍션 금지.

스키마 / 마이그레이션
================================================================
supabase/migrations 에 SQL을 둔다. Hibernate ddl-auto에 의존하지 않는다.
- PK: bigserial / identity. 프론트 number id 유지.
- join_code CHAR/VARCHAR(6) UNIQUE
- artifacts.status CHECK (PENDING, PROCESSING, READY, FAILED)
- tags, embedding TEXT (JSON 문자열)
- artifact_groups 테이블명 유지 (group 예약어 회피)
- 인덱스: join_code unique, artifacts(space_id), artifacts(group_id), members(space_id)
- created_at / updated_at timestamptz

기존 Spring이 만든 테이블이 있으면 이번 마이그레이션과 맞춰 정리한다.
로컬 MySQL 데이터 이전 스크립트는 만들지 않는다.
