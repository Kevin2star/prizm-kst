================================================================
제품 컨텍스트
================================================================
이 서비스의 핵심 순간은 4~5단계다.
아무도 "정리해줘"라고 요청하지 않았는데, 다른 사람이 올리면 내 화면이 스스로 정리된다.
GPT처럼 물어봐야 답하는 제품이 아니라, 남이 올리면 내 화면이 바뀌는 제품이다.

================================================================
백엔드
================================================================
Supabase Realtime (postgres_changes). STOMP/SockJS를 쓰지 않는다.

프론트는 artifacts / artifact_groups / members 를 space_id 필터로 구독한다.

이벤트 페이로드(프론트 onEvent 타입 유지):
  1) ARTIFACT_ADDED
     { "type": "ARTIFACT_ADDED", "artifact": { id, title, status, member... } }
     - 업로드가 PENDING 저장 직후. 분석 완료를 기다리지 않는다.
  2) GROUPS_UPDATED
     { "type": "GROUPS_UPDATED", "groupId": 1 }
     - 그룹 배정/정리본이 끝난 뒤. 프론트는 graph를 다시 조회해도 된다.
  3) MEMBER_JOINED
     { "type": "MEMBER_JOINED", "nickname": "지현", "major": "컴퓨터공학" }

================================================================
프론트
================================================================
- 스페이스 페이지 진입 시 connectSpaceRealtime(spaceId)
- ARTIFACT_ADDED: 트리/목록에 노드 추가 (또는 graph 재조회)
- GROUPS_UPDATED: 해당 가지를 갱신. 전체 물리 재배치는 하지 않는다.
- 페이지 unmount 시 구독 해제
- Realtime 연결 성공 시 폴링을 끈다. 실패 시 3초 폴링을 유지한다.

데모에서 중요한 UX:
  발표자 화면이 열려 있는 동안, 다른 노트북에서 업로드하면
  요청 버튼 없이 메인 트리가 바뀌어야 한다.

================================================================
하지 말 것
================================================================
- Kafka, Redis Pub/Sub, Socket.io, Spring STOMP를 새로 들이지 않는다. Supabase Realtime이면 충분하다.
- 인증 핸드셰이크를 복잡하게 만들지 않는다. spaceId만으로 구독한다.
- 메시지에 embedding 벡터 전체를 넣지 않는다. 용량 낭비다.

================================================================
완료 기준
================================================================
- 브라우저 두 개(또는 두 프로필)를 같은 스페이스에 켠다.
- A가 업로드하면 B 화면에 노드가 수 초 내 나타난다.
- 분석이 끝나 그룹이 생기면 B의 트리에 그룹 가지/배지가 갱신된다.
- 새로고침 없이도 발생해야 한다. 이것이 제품의 데모 하이라이트다.
