역할: 시니어 백엔드 엔지니어. 이미 동작하는 Spring Boot + JPA 앱의 DB만 교체한다.
선행 단계: 01~13이 구현되어 있거나, 최소한 backend가 JPA로 MySQL에 붙어 있어야 한다.
이번 단계 목표: 로컬 MySQL을 제거하고, DB를 Supabase(호스티드 PostgreSQL)로 바꾼다.
다음 단계: 없음. 이 단계는 스택 변경 패치다. 제품 기능(F1~F6)을 새로 만들지 않는다.

================================================================
왜 이렇게 바꾸나
================================================================
해커톤에서 로컬 MySQL 설치·계정·포트 문제를 없앤다.
팀원 모두 같은 원격 DB를 쓰거나, 각자 자기 Supabase 프로젝트를 쓰면 된다.
Supabase Auth / Storage / Realtime / Edge Functions로 백엔드를 대체하지 않는다.
Gemini 파이프라인, 그룹핑, STOMP는 계속 Spring Boot가 담당한다.

================================================================
고정할 아키텍처 (변경 금지)
================================================================
- 백엔드: Spring Boot 3 + Spring Data JPA. REST/WebSocket API의 단일 소스.
- DB: Supabase Postgres. JDBC로만 연결한다.
- 벡터: 계속 JSON 문자열 컬럼에 저장하고, 코사인 유사도는 자바로 계산한다.
  pgvector, Pinecone, Supabase Vector를 도입하지 않는다.
- 인증: 로그인 없음. 6자리 joinCode. Supabase Auth를 켜지 않는다.
- 프론트: React는 기존처럼 Spring API만 호출한다.
  @supabase/supabase-js 로 테이블을 직접 읽거나 쓰지 않는다.
- 실시간: 기존 Spring WebSocket + STOMP를 유지한다.
  Supabase Realtime으로 대체하지 않는다.

연결 방식:
  Spring datasource → Supabase Database connection string (Postgres)
  사용 계정은 Database 비밀번호를 가진 postgres(또는 동등한 DB 유저)다.
  anon/service_role API 키로 JPA를 붙이지 않는다.

================================================================
환경변수 (시크릿 값은 커밋하지 말 것)
================================================================
유지:
  DB_URL, DB_USERNAME, DB_PASSWORD
  GEMINI_API_KEY, GEMINI_TAG_MODEL, GEMINI_EMBED_MODEL
  VITE_API_BASE_URL

의미 변경:
  DB_URL      jdbc:postgresql://<host>:<port>/postgres?sslmode=require
  DB_USERNAME postgres 또는 풀러가 요구하는 postgres.<project-ref>
  DB_PASSWORD Supabase 프로젝트 Database password (Dashboard에서 확인)

권장 연결 (JPA/Hibernate 호환):
  - Session mode pooler 또는 Direct connection을 쓴다.
  - Transaction mode(PgBouncer, 보통 6543)는 prepared statement와 충돌할 수 있다.
    쓰려면 반드시 문서에 맞게 하고, 기동이 실패하면 Session/Direct로 되돌린다.
  - sslmode=require 를 붙인다.
  - 로컬 머신이 IPv6를 못 쓰면 Direct host 대신 Pooler(IPv4)를 쓴다.

예시 (값은 더미, 실제 호스트는 Dashboard > Connect 에서 복사):
  DB_URL=jdbc:postgresql://aws-0-ap-northeast-2.pooler.supabase.com:5432/postgres?sslmode=require
  DB_USERNAME=postgres.xxxxxxxxxxxxxxxxxxxx
  DB_PASSWORD=

application.yml에 명시할 것:
  spring.datasource.driver-class-name=org.postgresql.Driver
  (dialect는 Spring Boot 3 / Hibernate 6가 Postgres를 자동 감지해도 된다)

구현할 것
================================================================
1) Maven
   - mysql-connector-j 를 제거한다.
   - org.postgresql:postgresql (runtime) 를 추가한다.

2) JPA 엔티티
   - MySQL 전용 columnDefinition을 제거하거나 Postgres에 맞게 바꾼다.
     LONGTEXT → TEXT (또는 jsonb를 쓸 거면 tags/embedding만 jsonb)
   - tags, embedding은 기존처럼 JSON 문자열 컬럼으로 둬도 된다. 동작이 우선이다.
   - GenerationType.IDENTITY 는 Postgres에서 유지해도 된다.
   - 테이블명 artifact_groups 는 이미 group 예약어를 피하고 있으니 유지한다.
   - 엔티티 필드명·관계·인덱스 의미는 02_data_model.txt 와 같게 둔다.

3) 설정·문서
   - application.yml, application-example.yml, 루트 .env.example, README.md
     에서 MySQL 전제를 Postgres/Supabase 전제로 바꾼다.
   - README 사전 요구사항: 로컬 MySQL 설치 대신
     "Supabase 프로젝트 1개 + Database password + JDBC 연결 정보"
   - CREATE DATABASE prizm SQL 은 삭제한다. Supabase는 기본 DB가 postgres 다.
   - PowerShell 환경변수 예시를 JDBC Postgres URL로 교체한다.
   - 시크릿이 커밋되지 않는지 .gitignore를 다시 확인한다.

4) 프롬프트 정합
   - prompts/00_index.txt 기술 스택의 DB 줄을
     "Supabase Postgres (벡터는 JSON 컬럼, JDBC)" 로 고친다.
   - prompts/01_project_scaffolding.txt, prompts/02_data_model.txt 의
     MySQL 문구를 Supabase/Postgres 기준으로 고친다.
     (이후 에이전트가 다시 MySQL로 되돌리지 않게)

5) 기동 확인
   - ddl-auto=update 를 유지해도 된다. 시간 절약.
   - backend를 띄워 테이블이 Supabase에 생기는지 Dashboard Table Editor로 확인한다.
     기대 테이블: spaces, members, artifacts, artifact_groups
     (실제 이름은 엔티티 @Table 을 따른다)
   - GET /api/health 200
   - 데모 시드(CAFE01)가 돌아가면 기존과 같이 시드가 들어가는지 확인한다.
   - 프론트는 코드 변경이 없어도 된다. API가 살아 있으면 기존 화면이 동작해야 한다.

6) 로컬 MySQL 의존 제거
   - README, 스크립트, 주석에서 localhost:3306 / jdbc:mysql 을 남기지 않는다.
   - Docker Compose로 MySQL을 띄우는 안내가 있으면 삭제한다.

================================================================
하지 말 것
================================================================
- 프론트를 Supabase 클라이언트에 직접 붙이지 않는다.
- Auth, Storage, Edge Functions, Realtime, RLS 정책을 "제대로" 설계하느라
  시간을 쓰지 않는다. 백엔드가 postgres 계정으로 붙으면 RLS는 우회된다.
  해커톤 P0에서는 RLS를 켜지 않는 편이 안전하다.
- pgvector 마이그레이션, 임베딩 컬럼 타입 변경, 유사도 SQL화는 하지 않는다.
- Flyway/Liquibase를 새로 도입하지 않는다. 필수는 아니다.
- 기존 MySQL 데이터 마이그레이션 스크립트는 만들지 않는다.
  로컬 데모 데이터는 시더가 다시 넣으면 된다.
- 기능 API, Gemini, 그룹핑, 마인드맵 UI를 이 단계에서 리팩터하지 않는다.
- SUPABASE_URL / SUPABASE_ANON_KEY 를 프론트에 넣어서 DB를 열지 않는다.

================================================================
작업 순서 (에이전트는 이 순서를 지킨다)
================================================================
A. 현재 MySQL 의존 위치를 전부 찾는다 (pom, yml, 엔티티 columnDefinition, README, prompts).
B. 드라이버와 설정을 Postgres로 바꾼다.
C. 엔티티의 MySQL 전용 타입을 고친다.
D. 문서·예시 env·프롬프트를 맞춘다.
E. 사용자가 Dashboard에서 복사한 연결 정보가 환경변수로 들어온다는 전제로
   기동 방법을 README에 적는다. 실제 비밀번호를 파일에 쓰지 않는다.
F. 가능하면 backend를 기동해 컨텍스트 로딩과 시드를 확인한다.
   연결 정보가 없으면 컴파일/테스트까지 하고, README에 "Connect 문자열 필요"를 명시한다.

완료 기준
================================================================
- pom.xml에 mysql 커넥터가 없고 postgresql 드라이버가 있다.
- 코드/문서에 jdbc:mysql 과 "로컬 MySQL 필수" 안내가 없다.
- Spring이 Supabase Postgres에 붙어 테이블을 만들고 조회할 수 있는 설정이다.
- 프론트는 기존 Spring API를 그대로 쓴다.
- 00/01/02 프롬프트의 DB 스택이 Supabase로 통일되어 있다.
- GET /api/health 가 기동 후 200이다 (연결 정보가 있는 경우).
- 데모 시드 스페이스 CAFE01 이 기존과 같이 동작한다 (연결 정보가 있는 경우).
